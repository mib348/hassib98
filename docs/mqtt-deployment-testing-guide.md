# MQTT Deployment & Testing Guide

> Current public endpoint policy: external MQTT uses `mqtt.sushi.catering:443`,
> dashboard uses `https://mqtt.sushi.catering:8885/login` and
> `https://mqtt.sushi.catering:8885/ui`, and Laravel keeps using
> `127.0.0.1:1883`. See `docs/mqtt-sushi-catering-public-endpoints.md` for the
> aaPanel/Nginx proxy details.

## What We Built (Quick Recap)

```
Shopify Order Webhook
        |
        v
  OrdersCreateJob
        |
        |---- new order ----------> {env}/location/{slug}/orders/new

Shopify Cancelled Webhook
        |
        v
  OrdersCancelledJob
        |
        |---- cancelled order ----> {env}/location/{slug}/orders/cancelled

Shopify Updated Webhook
        |
        v
  OrdersUpdatedJob
        |
        |---- changed order ---------> {env}/location/{slug}/orders/updated

RPi reconnects after an outage
        |
        |---- orders.sync.request ---> {env}/location/{slug}/orders/sync
        |<--- orders.sync.response --- same topic, fresh Shopify snapshot

MQTT Broker (Mosquitto)  --->  RPi Device
        ^                          |
        |                          |
  RPi connects with           RPi sends fulfillment
  ClientId = location slug         |
                                   v
                          mqtt:subscribe command  --->  Fulfillment DB + Shopify metafields
```

## MQTT Client IDs and Topic Contract

Each Raspberry Pi must set its MQTT `ClientId` to the location slug it owns.
The dashboard displays this received `ClientId` as the location identity.
If a client connects without a `ClientId`, Mosquitto generates an `auto-*`
value and the dashboard marks it as autogenerated.

Examples:

| Location | MQTT ClientId | Subscribe for server events | Bidirectional order sync | Publish fulfillment | Publish Pi status |
|---|---|---|---|---|---|
| Standort 1 | `standort_1` | `{env}/location/standort_1/orders/new`, `{env}/location/standort_1/orders/cancelled`, `{env}/location/standort_1/orders/updated` | `{env}/location/standort_1/orders/sync` | `{env}/location/standort_1/orders/fulfilled` | `{env}/location/standort_1/pi/status` |

Current topic shapes:

```text
{env}/location/{location_slug}/orders/new
{env}/location/{location_slug}/orders/cancelled
{env}/location/{location_slug}/orders/updated
{env}/location/{location_slug}/orders/fulfilled
{env}/location/{location_slug}/orders/sync
{env}/location/{location_slug}/pi/status
{env}/location/{location_slug}/pi/check
{env}/location/{location_slug}/pi/command
```

`{env}` is controlled by `MQTT_TOPIC_ENV`, usually `dev` or `live`.

The Pi should publish status every 10 seconds with QoS 1 and retain=true.
Laravel subscribes to the current environment only via `{env}/location/+/pi/status`.
Node-RED listens to both `dev/location/+/pi/status` and `live/location/+/pi/status`
and marks an online device offline after more than 20 seconds without a new
heartbeat.

Heartbeat payload:

```json
{
  "event": "pi.status",
  "client_id": "standort_1",
  "location_slug": "standort_1",
  "status": "online",
  "timestamp": "2026-06-03T10:00:00+02:00",
  "uptime_seconds": 3600,
  "app_version": "1.0.0",
  "ip_address": "192.168.1.10",
  "wifi_connected": false,
  "eth_connected": true,
  "wifi_strength": null,
  "cpu_temp": 52.6,
  "temperature": 4.8,
  "download_mbps": 95.4,
  "upload_mbps": 18.7,
  "ram_usage": 24.2,
  "disk_usage": 17.9,
  "lock_status": "locked",
  "door_sensor_status": "closed",
  "message": null
}
```

`cpu_temp` is the CPU temperature in degrees Celsius. `temperature` is the
temperature inside the vending machine; the dashboards display these as two
separate metrics and never use one as a fallback for the other.
`download_mbps` and `upload_mbps` are numeric internet-speed values in Mbps.
`eth_connected` and `wifi_connected` are booleans. When Ethernet is active,
send `eth_connected: true` and `wifi_connected: false`; the dashboards will
display `Ethernet` instead of treating the missing WiFi connection as an
offline device.

The server-derived timeout follows the two-heartbeat rule: exactly 20 seconds
since the last received heartbeat is still online, and more than 20 seconds is
offline.

### Manual Device Commands

The **Check PI Response** action uses the existing lightweight health-check
topic, independently of the speed-test command:

```text
{env}/location/{location_slug}/pi/check
```

The Pi must subscribe to this exact topic and publish its normal `pi.status`
heartbeat immediately after receiving this QoS 1, non-retained request:

```json
{
  "event": "pi.check",
  "location": "Test Location",
  "location_slug": "test_location",
  "requested_at": "2026-08-23T13:40:21+03:00"
}
```

This legacy check must not run a speed test. It only lets Tech Admin distinguish
broker acceptance from a device that actually returned a fresh heartbeat.

Tech Admin publishes commands to the selected location's exact topic:

```text
{env}/location/{location_slug}/pi/command
```

The Pi must subscribe to this topic and handle only these command values:

```json
{
  "event": "command",
  "command": "test_internet_connection",
  "timestamp": "2026-08-23T13:40:21+03:00"
}
```

```json
{
  "event": "command",
  "command": "restart_device",
  "timestamp": "2026-08-23T13:42:05+03:00"
}
```

Both commands use QoS 1 and `retain=false`. After
`test_internet_connection`, include the measured `download_mbps` and
`upload_mbps` in the next `pi/status` heartbeat. Tech Admin reports separately
whether Laravel published to the broker and whether a newer heartbeat was
received; a published command without a fresh heartbeat does not prove that
the device executed it.

MQTT Last Will should publish to the same topic with QoS 1 and retain=true:

```json
{
  "event": "pi.status",
  "client_id": "standort_1",
  "location_slug": "standort_1",
  "status": "offline",
  "timestamp": "2026-06-03T10:00:00+02:00",
  "message": "MQTT client disconnected unexpectedly"
}
```

### Reconnect Order Synchronization

Live `orders/new`, `orders/updated`, and `orders/cancelled` messages cannot by
themselves recover an order published while the Pi was offline. After every
successful reconnect, the Pi requests a complete location snapshot on:

```text
{env}/location/{location_slug}/orders/sync
```

The request and response use this same topic with QoS 1 and `retain=false`.
Subscribe before publishing. The `event` value separates the two directions.

Device request:

```json
{
  "event": "orders.sync.request",
  "request_id": "2db9d18d-d6c8-4acd-82dd-7f35704d22d9",
  "client_id": "test_location",
  "location_slug": "test_location",
  "requested_at": "2026-07-22T10:00:00+02:00",
  "reason": "mqtt_reconnect"
}
```

Laravel processes only `orders.sync.request`. The topic slug, `client_id`, and
payload `location_slug` must match. Laravel queries Shopify GraphQL directly and
publishes this response to the same topic:

```json
{
  "event": "orders.sync.response",
  "success": true,
  "request_id": "2db9d18d-d6c8-4acd-82dd-7f35704d22d9",
  "client_id": "test_location",
  "location_slug": "test_location",
  "generated_at": "2026-07-22T10:00:02+02:00",
  "from_date": "2026-07-22",
  "to_date": "2026-07-29",
  "complete": true,
  "order_count": 1,
  "orders": [
    {
      "event": "order.snapshot",
      "order_id": 12345,
      "order_number": 1001,
      "pick_up_date": "22-07-2026",
      "location": "Test Location",
      "location_slug": "test_location",
      "items": [
        {
          "product_id": 987,
          "title": "Sushi Box",
          "quantity": 2
        }
      ],
      "customer_name": "Customer Name",
      "total_price": "20.00",
      "financial_status": "PAID",
      "fulfillment_status": "UNFULFILLED",
      "custom_status": [],
      "state": "active",
      "cancel_reason": null,
      "cancelled_at": null,
      "created_at": "2026-07-22T08:00:00Z",
      "updated_at": "2026-07-22T08:00:00Z"
    }
  ]
}
```

Device processing rules:

1. Ignore its own `orders.sync.request` message.
2. Accept only `orders.sync.response` with the outstanding `request_id`.
3. Replace the local snapshot only when `success=true` and `complete=true`.
4. An empty `orders` array with `complete=true` means the snapshot is empty.
5. Keep existing local data when `complete=false`, then retry the request.
6. Continue listening to the three live order event topics after synchronization.

Every request triggers a fresh Shopify query. The snapshot covers pickup dates
from today through seven days ahead in `Europe/Berlin` and includes active,
cancelled, refunded, partially refunded, and fulfilled states.

## STEP 1: Start the Mosquitto Broker on the Server

SSH into the Ubuntu server that hosts the Laravel project and run:

```bash
cd /path/to/laravelshopifypartnerapp    # wherever docker-compose.yml lives
docker compose up -d
```

Verify all 3 containers are running:

```bash
docker compose ps
```

You should see:
- `mosquitto` — healthy
- `mqtt-web-client` — running (Node-RED dashboard behind `mqtt.sushi.catering:8885`)

**If already running, skip this step.**

---

## STEP 2: Add MQTT Variables to `.env` on the Server

SSH into the server and edit the Laravel `.env` file:

```bash
nano /path/to/laravelshopifypartnerapp/.env
```

Add these lines at the bottom:

```env
MQTT_HOST=127.0.0.1
MQTT_PORT=1883
MQTT_CLIENT_ID=laravel-server
MQTT_SUBSCRIBER_CLIENT_ID=laravel-subscriber
MQTT_AUTH_USERNAME=mqtt_12342026
MQTT_AUTH_PASSWORD=mqtt_12342026
MQTT_TLS_ENABLED=false
MQTT_TLS_CERT_DIR=/www/server/panel/vhost/cert/mqtt.sushi.catering
MQTT_TLS_LOCAL_PORT=9443
MQTT_DASHBOARD_LOCAL_PORT=1885

# Optional order-sync overrides; these are the built-in defaults.
MQTT_ORDER_SYNC_LOOKBACK_DAYS=15
MQTT_ORDER_SYNC_WINDOW_DAYS=7
MQTT_ORDER_SYNC_TIMEZONE=Europe/Berlin
```

Save and exit (`Ctrl+X`, `Y`, `Enter`).

Then clear the config cache:

```bash
php artisan config:clear
```

## STEP 8: Set Up Supervisor (Production)

The `mqtt:subscribe` command needs to run 24/7. Supervisor keeps it alive.

SSH into the server:

```bash
# Install supervisor if not already installed
sudo apt install supervisor

# Create config file
sudo nano /etc/supervisor/conf.d/mqtt-subscriber.conf
```

Paste this (adjust the path):

```ini
[program:mqtt-subscriber]
process_name=%(program_name)s
command=php /path/to/laravelshopifypartnerapp/artisan mqtt:subscribe
autostart=true
autorestart=true
numprocs=1
user=www-data
redirect_stderr=true
stdout_logfile=/path/to/laravelshopifypartnerapp/storage/logs/mqtt-subscriber.log
stopwaitsecs=10
```

Then:

```bash
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl start mqtt-subscriber
```

Check it's running:

```bash
sudo supervisorctl status mqtt-subscriber
```

Should show `RUNNING`.

## Quick Troubleshooting

| Problem | Check |
|---------|-------|
| "Connection refused" | Is Mosquitto running? `docker compose ps` |
| "TLS handshake failed" | For Laravel, use `MQTT_PORT=1883` and `MQTT_TLS_ENABLED=false`; for external clients, verify `mqtt.sushi.catering:443` routes to `127.0.0.1:9443` |
| "Not authorized" | Check username/password match in `.env` and `docker-compose.yml` |
| Tinker publish works but no message in dashboard | Check Node-RED is connected to the internal broker |
| Subscriber doesn't receive messages | Make sure subscriber is running. Check topic name matches exactly |
| Sync request appears but no response | Check both the queue workers and MQTT subscriber in Supervisor, then inspect `storage/logs/laravel.log` for `MQTT order sync` |
| Sync response has `complete=false` | Shopify could not be queried; keep local device data and retry rather than clearing it |
| Shopify metafield errors on test data | Expected — use a real order_id for metafield sync testing |

## Ports Reference

| Port | Protocol | Purpose |
|------|----------|---------|
| 443 | MQTT+TLS | Public external MQTT via `mqtt.sushi.catering` |
| 9443 | MQTT+TLS | Local Nginx stream target for Mosquitto TLS |
| 1883 | MQTT plain | Local Laravel/internal broker access only |
| 1885 | HTTP | Local Node-RED target |
| 8885 | HTTPS | Public dashboard at `mqtt.sushi.catering:8885` |
